# AGENTS.md

This repo is ticket-pilot, the owner's Asana -> git worktree + headless agent -> PR -> review pipeline. See README.md for the flow.

- Backend: Python 3 stdlib only (no pip deps). Entry point: `bin/tp` (`ticket_pilot/cli.py`).
- 사용 흐름(태그, 단계, 승인, 배포, 화면)을 바꾸는 PR은 `docs/guide.md`도 같이 고친다 (`tp guide`, 대시보드 도움말이 이 파일을 보여 줌).
- Web UI: `web/` is React + Vite + Tailwind v4. Use the `web/src/ui` components and the tokens in `web/src/theme/tokens.css`
  only (no raw hex / Tailwind default greys, no `bg-primary/10`-style opacity shades); `cn` only joins classes, so do not
  pass two classes for the same property. No private registries: `npm ci` must work without a `~/.npmrc`. Never commit `web/node_modules/` or `web/dist/`.
- The SQLite DB lives in `data/` and is gitignored. Never commit `data/`.
- Asana is read-only from this tool, with one exception the owner approved (2026-10-19): a ticket is marked completed once its change is verified live in production (`release.finalize` for the train and dashboard deploys, `track.py` for merges made elsewhere), in every repo. Chat and ticket agents may also write through `tp asana comment|create|update|tag` (`ticket_pilot/asana_write.py`, TP-97; off with `global.agent_asana_write`; agents run unsandboxed, so that switch is a guard for well-behaved agents, not a security boundary); each write is an `asana_write` event. Do not add other Asana writes unless the owner asks.
- GitHub issues of repos in the `github_issues` setting (`tp config get global.github_issues`) are tickets too (2026-10-20); repos of a `source: github` project only take open issues labeled `tp` (TP-92). The same completion step closes the issue.
- Milestones (2026-10-30): subtasks of an Asana parent tagged with the `milestone_tag` setting (default `tp-milestone`; older installs keep `orca-milestone`) go into `milestone/<parent gid>`; host code (`ticket_pilot/milestone.py` + `process_approvals`) merges a subtask PR there as soon as the AI review approves it. The milestone PR opens only after the owner presses 마일스톤 작업 완료 (cleared mechanically when a subtask is in progress again), and its staging merge still needs their dashboard approval. Never merge into a milestone branch from an automation prompt or agent.
- This repo deploys itself: merging into `main` runs `.github/workflows/deploy.yml` on the owner's Mac (self-hosted runner), which fast-forwards the host checkout, builds `web/dist` and restarts the dashboard and tick launchd agents (`launchd/install.sh`; dashboard on port 3032). Keep the host checkout on `main`; do ticket work in worktrees.
- No Orca: `tp tick` (launchd, every minute) runs the automations, `ticket_pilot/runner.py` creates ticket worktrees with `git worktree` and starts `codex exec` / `claude -p` detached; agents report with `tp ws-set`. Orca code paths left in the repo only serve runs Orca started before the switch.
- A host process and a container process never share one `tp.db` over a bind mount (TP-8: SQLite locks do not cross it and the DB gets corrupted). Docker mode (`docker/`, TP-164) keeps its DB only in a named volume and only processes inside the container write it.
- The Asana PAT comes from the keychain (`ticket-pilot-asana`) or `ASANA_PAT`. Never print or log it.
- When running as an automation's AI step (`tp tick`), follow the prompt in `prompts/automation_*.md` and only use `bin/tp`, `gh`, and read-only inspection. Do not modify code in other repos.
- Offline testing: `TP_DB=/tmp/x.db bin/tp config set global.asana_workspace_gid '"1"'` once (sync stops without a workspace), then `TP_DB=/tmp/x.db TP_ASANA_FIXTURE=<json path->response map> bin/tp sync`.
- Production releases only happen through deterministic host code: the weekday train (`ticket_pilot/release.py`) and deploys the owner requests on the 배포 page (`ticket_pilot/deploy.py`, rules in the per-repo deploy settings, `tp config get repo.<name>.deploy`; the owner approved running them immediately, 2026-10-19). Never merge `staging -> main` or merge PRs from an automation prompt.
- Settings (repos, deploy rules, checks, Asana links, global values) live in `data/tp.db` since TP-49, edited on the dashboard 설정 page or with `tp config`; git has only `config/*.example.json`. Never commit `config/settings.json` or `config/project_map.json`.
- Worktree removal: only `ticket_pilot/cleanup.py` removes worktrees, and only ticket worktrees (`runs.worktree_path`) whose merged PRs are all verified in production (2026-10-19: remove right away, delete the local branch too), or whose ticket is skipped (건너뜀, e.g. dropped; 2026-10-23: remove even with local changes, once no agent or dev server runs there). Never remove manually created worktrees (git or Orca), remote branches, or worktrees from an automation prompt.
