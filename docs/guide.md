# toothpaste (치약) 사용 설명서

Squeeze a ticket, get a PR. 명령어 `tp`는 **T**ooth**P**aste의 줄임이에요.

toothpaste(치약)는 Asana 태스크와 GitHub 이슈를 받아 git worktree에서 에이전트(Codex / Claude)가 일하게 하고, PR, AI 리뷰,
staging 머지, 프로덕션 배포까지 이어 주는 도구입니다. 각 절의 `## <키> · <제목>`의 키로 `tp guide <키>`를 실행하면 그 절만 볼 수 있어요.

## start · 시작하기
설치한 뒤 할 일과 대시보드 화면 안내.

설치는 `gh repo clone bini59/toothpaste ~/tp-work/app` 다음 `~/tp-work/app/bin/tp setup`입니다. macOS와 Linux(systemd)에서
같은 두 줄로 설치해요. setup이 빠진 것(Python 3.11 이상, git, gh 로그인, claude, codex, agy 중 하나 등)을 먼저 알려 주고, 다 있으면 대시보드와
1분마다 도는 tick을 백그라운드로 띄웁니다(macOS는 launchd, Linux는 systemd 사용자 서비스). 그다음 열어 주는
**시작하기** 화면(`#start`)에서 다섯 단계를 마칩니다. 브라우저가 없는 서버에서는 주소만 출력하니 그 주소를 여세요.

Linux에서 알아 둘 것:
- 로그아웃해도 계속 돌게 하려면 linger를 켭니다: `sudo loginctl enable-linger $USER`. setup은 꺼져 있으면 알려만 주고 직접 켜지 않아요.
- `systemctl --user`가 동작해야 해요. su로 바꾼 셸, WSL, 컨테이너에서는 보통 안 되니 그 사용자로 직접 로그인해서 설치하세요.
- 로그는 `~/tp-work/logs`(`dashboard.log`, `tick.log`)와 `journalctl --user -u ticket-pilot-dashboard`에 있어요.
- 토큰은 키체인 대신 `~/.config/ticket-pilot/secrets.json`(권한 600)에 저장해요.

Docker로 실행하기(선택, 기본은 위의 호스트 설치):
1. `cp docker/.env.example docker/.env` 후 `TP_ADMINS`(GitHub 아이디, 쉼표 구분)나 `TP_ORG`(이 조직 멤버도 허용)를 넣습니다. 둘 다 비면 시작하지 않아요.
2. macOS 또는 Linux의 Docker 호스트에서 저장소 폴더를 열고 `python3 -m ticket_pilot.docker_update_manager install`을 실행하세요. 대시보드와 업데이트 관리자가 함께 설치돼요. `http://127.0.0.1:3032`에서 GitHub로 로그인합니다.
3. 시작하기의 **에이전트 로그인** 단계(설정 → 에이전트 → 활성 계정과 같은 화면)에서 버튼으로 로그인해요. 터미널이 필요 없어요.
4. `TP_ADMINS` 계정은 **설정 → 고급 → 업데이트**에서 새 릴리즈를 설치할 수 있어요. `tp setup`, `tp migrate`, 로컬망 공유는 Docker 모드에서 쓰지 않아요.
- 컨테이너를 멈추거나 다시 빌드하면(업데이트 포함) 그 안에서 돌던 에이전트도 끝나요. 작업 중인 티켓이 없을 때 업데이트하세요.
- 에이전트가 Docker를 써야 하는 저장소는 안 되고, 맥 Docker Desktop에서는 파일 입출력이 느려요.

Docker 모드 외부 공개(선택, Cloudflare Tunnel). 모든 접속이 GitHub 로그인을 거치는 Docker 모드에서만 써요(호스트 설치는 공개하지 마세요):
1. Cloudflare Zero Trust → Networks → Tunnels → 터널 만들기 → 토큰을 복사해 `docker/.env`의 `TUNNEL_TOKEN`에 넣습니다.
2. Public hostname: `tp.example.com` → `http://tp:3032`.
3. `docker/.env`에 `TP_PUBLIC_URL=https://tp.example.com`을 넣고, `docker/`에서 `docker compose -f compose.yaml -f compose.update.yaml --profile tunnel up -d`를 실행하세요. 기존 `compose.override.yaml`이 있으면 `-f compose.update.yaml` 바로 앞에 `-f compose.override.yaml`을 넣으세요.
4. **강력 권장**: Cloudflare Access로 회사 이메일이나 IdP 조건을 걸어 GitHub 로그인 앞에 한 겹 더 잠그세요.
5. **위험**: 로그인한 사람은 채팅 에이전트로 컨테이너 안에서 명령을 실행할 수 있어요.
- 상태는 **설정 → 고급 → 외부 공개**(TP_ADMINS만)에서 봐요: 터널 연결 여부, 공개 주소. 토큰과 도메인은 화면에서 받지 않아요.
  호스트 모드에서는 이 카드에 "Docker 모드에서만 쓸 수 있어요" 안내만 나와요.
- `TP_PUBLIC_URL`이 있으면 로그인 쿠키가 HTTPS 전용(Secure)이 되고, 쓰기 요청은 그 주소나 `http://127.0.0.1:<포트>`에서만 받아요.
  접속 기록의 IP는 Cloudflare가 알려 준 방문자 IP(`Cf-Connecting-IP`)이고, 기록에만 써요.

실행 방식 바꾸기(호스트 ↔ Docker): 이미 호스트에 설치해서 쓰고 있으면 **설정 → 고급 → 실행 방식**이나 `bin/tp mode`로 바꿔요.
1. `bin/tp mode`: Docker 환경 점검(docker 명령, 실행 중, compose v2, 디스크, CPU, 맥 파일 공유). 모두 통과해야 바꿀 수 있어요.
2. `bin/tp mode docker`: 미리보기(연결할 경로, 관리자, 옮길 토큰, 주의할 점). 아무것도 바꾸지 않아요. 관리자는 `--admins 아이디,아이디`(기본은 연결된 GitHub 계정).
3. `bin/tp mode docker --apply`: 실행 중인 에이전트, 자동화, 채팅, dev 서버, tp check가 없을 때만 해요. DB 백업 → Docker volume, 토큰 이전, 저장소와 `~/.claude`, `~/.codex`를 같은 경로로 연결, 서비스 멈춤 → 컨테이너 시작. 끝나면 같은 주소에서 GitHub로 로그인해요. 호스트 DB는 읽기 전용 백업으로 남아요.
4. 돌아가기: 호스트에서 `bin/tp mode host --apply`(컨테이너 안에서는 못 해요).

Docker로 바꾼 동안에는 호스트 설치용 `tp update`, `tp setup`, `tp migrate`가 멈춰요. Docker 대시보드에서 업데이트하려면 아래 **업데이트** 항목의 관리자 설치를 한 번 진행하세요.
- 실패하면 끝난 단계와 되돌리는 방법을 보여 줘요. 고친 뒤 같은 명령을 다시 실행하면 이어서 해요(기록: `~/tp-work/mode-state.json`).
- 맥에서 컨테이너는 keychain의 Claude 로그인을 못 봐요. 컨테이너에서 claude 인증이 실패하면 **설정 → 에이전트 → 활성 계정**에서 claude에 로그인하세요.

1. Asana 연결 (선택): 사용한다면 Personal access token을 넣습니다(macOS는 키체인, Linux는 secrets.json에 저장). 사용하지 않으면 **Asana 사용 안 함**을 누르세요. GitHub 이슈는 Asana 없이도 동기화합니다.
2. GitHub 연결: 화면에 나온 코드로 Device Flow 로그인.
3. 에이전트 로그인: Claude, Codex, Antigravity 중 쓰는 것 하나. 이미 터미널에서 로그인돼 있으면 완료로 나와요(아래 **agent** 주제).
4. 사용자 이름: 에이전트가 질문하거나 보고할 때 부르는 이름.
5. 첫 프로젝트를 추가할 때 GitHub 레포와 티켓 출처(Asana 프로젝트, GitHub 이슈, Notion 데이터베이스)를 고릅니다.

`tp tick`이 1분마다 돌며 동기화, 투입, 리뷰, 배포를 진행합니다. 새 티켓은 보통 5분 안에 투입돼요.

대시보드 화면:
- **수신함**: 읽지 않은 채팅 답장과 파이프라인 알림.
- **보드**: 티켓을 단계별 열(대기, 작업 중, 막힘, PR / 리뷰 대기, 리뷰 완료, 배포 대기)로 보여 줍니다. 레포 선택, 답장, 승인, 그만두기를 여기서 합니다.
- **마일스톤**: 마일스톤별 하위 태스크, 작업 완료 버튼, dev 서버.
- **작업실**: 파이프라인을 공장처럼 그린 화면. 지금 누가 무엇을 하는지.
- **배포**: 티켓별, 레포별 배포 버튼, 진행 중인 배포, 배포 열차, staging에 있고 프로덕션에 없는 것, 이력.
- **프로젝트**: 레포별 채팅(읽기 전용 에이전트와 대화)과 레포 설정.
  - 채팅에서 “스크린샷을 보여 줘”라고 요청하면 에이전트가 `tp chat attach <경로>...`로 답변에 파일을 첨부해요.
    이미지 미리보기를 누르면 원본이 열리고, 다른 파일은 이름을 눌러 열 수 있어요. 답변 하나에 최대 10개, 파일당 20MB까지예요.
    첨부는 새로고침해도 남고 대화를 지우면 함께 삭제돼요.
  - Claude 채팅은 답변이 끝나고 50분 동안 새 메시지가 없으면, 컨텍스트가 10만 토큰 이상일 때만 틱에서 대화를 압축해요. 대화에
    **대화가 압축됐어요** 구분선이 생기고, 다음 메시지는 요약을 담은 새 세션에서 시작해요.
    이전 메시지는 화면에서 계속 볼 수 있어요.
- **티켓**: 전체 티켓 목록, 관계도(프로젝트와 레포 연결).
- **모니터링**: 배차 담당, 리뷰어, 배포 담당, 청소부 자동화의 실행 기록, 전체 로그, 시스템 자동화, 설정 이력(누가 언제 어떤 설정을 바꿨는지, 범위·사람·기간으로 거르기).
  **지표**에서 핵심 수치, 주간 추이, 시점 전후 비교, Claude 채팅 압축 집계와 기록을 확인해요.
- **설정**: 전역 값. 메뉴는 **에이전트**(활성 계정, 투입·리뷰·검사 카드), **Git · GitHub**(연결, 경로, GitHub 이슈), **Asana**(연결, 태그, 숨김 프로젝트), **Notion**(로그인, 연결 계정·워크스페이스), **배포 열차**, **테마**, **고급**(사용자 이름, 업데이트, 내보내기, 실행 방식, 로컬망 공유). 레포 설정은 프로젝트 → 레포 → 설정.
- **업데이트**: 새 버전이 있을 때만 사이드바에 나옵니다.
- **도움말**: 이 설명서.

## metrics · 지표
프로덕션 도달률과 티켓당 토큰을 보고 개선 시점 전후를 비교해요.

사이드바 **모니터링 → 지표**에서 **개요**, **주간 추이**, **시점 비교**, **채팅 압축** 탭을 열어요.
개요는 최근 12주간의 핵심 수치와 추이, 각 수치의 집계 기간과 표본 수를 보여 줘요. 휴대폰에서는 보고 싶은 핵심 지표를 선택해요.
주는 UTC 월요일에 시작하고, 각 티켓은 첫 프로덕션 확인(`prs.prod_at`)에 한 번 셉니다.

- **무개입 프로덕션 도달률**은 프로덕션 확인까지 `ws-set --status todo`의 BLOCKED 보고, 오너 답장·재개, 리뷰·검사 override,
  수동 수정 요청(`tp review-save --verdict changes`)이 없었던 티켓의 비율이에요. 이전 BLOCKED 보고는 수신함과 작업 상태 기록을 사용하며,
  수동 수정 요청은 지표 기능이 추가된 이후의 요청부터 구분할 수 있어요.
- **프로덕션 티켓당 토큰**은 첫 프로덕션 확인까지 tp가 시작한 작업·재작업·충돌 해결·리뷰 세션의 입력(캐시 포함)과 출력 토큰의 합이에요.
  사용량을 읽을 수 있는 티켓으로 평균을 내고 표본 수를 표시해요. Claude 하위 에이전트는 남아 있는 transcript의 토큰과 도구 호출을 합산해요.
  Claude 기록만 읽혔으면 **Claude만**이라고 표시해요.
- **주간 추이**에서 첫 AI 리뷰 승인율, 평균 수정 라운드, PR 생성 → 머지와 머지 → 프로덕션 소요 시간(머지 대상별 중앙값),
  도구 호출, 반복 패턴, 안정성 등 9개 지표 중 하나를 골라 크게 봐요. 차트 아래에서 주를 선택하면 값과 표본 수를 텍스트로 읽을 수 있어요.
  상세 집계 기준은 **계산 방법**에서 확인해요. 과거의 `ws-set` 누락은 종료·시간 초과 이벤트가 남은 경우만 세고,
  추적한 실행도 누락을 확인한 이벤트도 없는 기간은 빈 값으로 표시해요.

**시점 기록**을 누르거나 `tp mark "brief에 screenshot 사용법 추가"`를 실행하면 주간 차트에 세로선이 나타나요.
업데이트나 배포 후 tick이 활성 릴리즈 태그를 확인하면 버전 시점도 추가해요. 차트 위에서 시점을 선택하고 **비교 열기**를 누르거나
**시점 비교** 탭에서 바로 시점을 선택하면 직전과 직후의 같은 길이(기본 14일)를 비교해요. 표는 페이지를 넘겨 보고, 전체 수치와 표본은
행의 **상세**에서 확인해요. 비율·평균·중앙값의 표본이 10개 미만이면 흐리게 표시해요. 이후 기간이 끝나기 전에는 관측한 만큼 양쪽에서 비교해요.

**채팅 압축**에서 최근 7일·30일·90일 또는 전체 기간의 Claude 채팅 압축 횟수, 성공·실패, 압축 비용, 추정 순절감량,
성공한 압축 중 후속 대화가 없는 건수와 비용을 봐요. **추이**에서 7일·30일은 일별, 90일은 UTC 월요일부터 주별, 전체는 월별로 횟수와 토큰을 확인해요.
**압축 기록**은 페이지를 넘기고 행의 **상세**에서 압축 전후 토큰과 측정 턴을 읽어요. 검색에서 **채팅 압축**을 선택하거나 기존 `#chat-compactions` 주소를 열어도 이 탭으로 이동해요.

압축 전 마지막 턴과 압축 후 첫 턴의 컨텍스트는 각각 마지막 API 호출의 입력 토큰(캐시 읽기·생성 포함)으로 비교해요.
요약을 받은 Claude 턴이 처음 성공하면 그 세션을 기준으로 후속 턴을 집계해요. 이 세션을 재개한 턴은 실패해도 사용량이 기록되면 계산에 포함해요.
추정 순절감량은 압축 전 컨텍스트와 이 세션의 각 측정 턴 간 차이를 더한 값에서 압축에 사용한 입출력 토큰(캐시 포함)을 빼요.
기간은 압축 완료일 기준이고 후속 턴은 기간 밖이어도 집계해요. 압축이 실패했거나 요약으로 이어진 Claude 세션이 없으면 기록된 압축 비용만 차감해요.
비용이 줄어든 토큰보다 크면 순절감량은 음수로 표시해요. 이전 기록이나 사용량을 읽을 수 없는 값은 `—`로 표시해요.

tick이 끝난 에이전트 실행을 로컬 transcript에서 한 번 집계해 DB에 저장해요. 설치 직후에는 남아 있는 과거 기록도 여러 tick에 걸쳐 채웁니다.
화면은 저장된 값만 읽어요. 집계 결과와 시점 기록은 로컬 DB에 저장돼요.

## ticket · 티켓
티켓 출처, 단계, 여러 레포 티켓, 의존 관계.

**티켓 만들기**

터미널과 프로젝트 채팅은 같은 명령을 사용해요. `--project`에는 프로젝트 설정의 ID를 넣으세요.

```sh
tp ticket create --project app --title "로그인 오류" --body "재현 순서" --assignee me --tag 버그
tp ticket create --project app --title "재현 테스트" --parent APP-12
tp ticket create --project app --title "모바일 수정" --milestone APP-24
```

프로젝트의 출처에 따라 Asana 태스크, Notion 작업 DB 페이지 또는 GitHub 이슈가 생깁니다. GitHub는 기본 레포에 만들고 기본 레포를 지정하지 않았으면 설정 순서상 첫 레포를 사용해요. 이슈에는 `tp` 라벨이 붙습니다. `--tag`는 여러 번 줄 수 있고, 하위 티켓에는 `--parent`와 `--milestone` 중 하나를 사용하세요.

성공하면 표준 출력에 `ok`, `source`, `key`, `gid`, `url`을 담은 JSON 한 줄이 나옵니다. 실패하면 표준 오류의 JSON에서 `code`와 `message`를 확인하세요. 종료 코드 4는 요청이나 설정을 고쳐야 한다는 뜻이에요. 예를 들어 `parent_not_found`면 부모 키를, `milestone_unsupported`면 마일스톤 연결과 staging 머지 설정을 확인하세요. `global.agent_asana_write`가 꺼져 있거나 자동화 단계에서 호출하면 `write_disabled`입니다. 외부 API나 로컬 저장 오류는 종료 코드 5와 `upstream_error`로 표시돼요. 오류 JSON에 `created`가 있으면 이미 생성된 티켓의 `key`, `gid`, `url`을 사용하세요.

**출처**
- Asana: 설정에서 사용을 끄면 동기화와 Asana 작업을 중지하며 기존 연결 정보와 티켓은 보존합니다. 다시 켜면 다음 동기화부터 재개합니다. Asana 연결에 오류가 나도 GitHub 이슈는 동기화합니다. 나에게 배정된 미완료 태스크에 설정 `asana_tag`의 태그(새 설치 기본 **`tp`**)를 붙이면 티켓이 됩니다. 태스크의 프로젝트가 설정에서 레포와 연결돼 있어야 해요.
- GitHub 이슈: 설정 `github_issues`에 있는 레포의 열린 이슈는 모두 티켓입니다(키 `TP-<번호>` 등). 출처가 `github`인 프로젝트의 레포는 라벨 `tp`가 붙은 열린 이슈만 받습니다. 라벨을 떼면 티켓이 빠지고, 다시 붙이면 돌아와요.
- Notion은 프로젝트에서 선택한 연결과 데이터 소스로부터 조건에 맞는 페이지를 가져옵니다. 페이지 ID가 티켓 키의 기준이라 제목이나 담당자가 바뀌어도 같은 티켓을 갱신해요.
- 티켓 번호는 Asana `ID` 커스텀 필드(예: `CRSC-340`), 없으면 `AS-<gid>`. worktree와 브랜치는 소문자 번호(`tp/crsc-340`)입니다.

**Notion OAuth 앱 등록 (운영자, 최초 배포)**

1. Notion 개발자 포털에서 ticket-pilot용 OAuth 앱을 만드세요. 앱을 만들 때 설치 범위가 정해지므로 사용할 회사·개인 워크스페이스를 모두 고르세요. 어느 워크스페이스에서나 로그인하도록 운영하려면 **Any workspace**를 선택하세요. 콘텐츠 읽기와 사용자 정보 읽기(이메일 제외) 권한을 켭니다. [Notion OAuth 앱 만들기](https://developers.notion.com/guides/authorization/overview#how-to-make-an-oauth-integration)
2. 로그인에 쓸 대시보드 주소 뒤에 `/notion/callback`을 붙여 앱에 리디렉션 주소로 등록하세요. 기본 로컬 주소는 `http://127.0.0.1:3032/notion/callback`이고, 공개 도메인으로 접속하면 해당 HTTPS 주소를 사용해요.
3. 대시보드를 실행하는 사용자로 서버에서 `bin/tp notion-app --client-id CLIENT_ID`를 실행하고 발급받은 시크릿을 숨김 프롬프트에 입력하세요. Docker 설치라면 저장소 루트에서 `docker compose -f docker/compose.yaml exec tp tp notion-app --client-id CLIENT_ID`를 실행합니다. 배포 스크립트에서는 같은 명령의 표준 입력에 시크릿 파일을 연결하세요(Docker에서는 `exec -T`). 앱 정보는 macOS 키체인 또는 Linux·Docker의 권한 600 비밀 파일에 저장됩니다.

이전 버전에서 OAuth 앱을 등록했다면 이 단계를 건너뛰세요. 업데이트 후에도 저장된 앱과 계정 연결을 사용하고 기존 프로젝트는 같은 DB와 필터로 동기화해요.

**Notion 계정 연결과 프로젝트 설정**

1. **전역 설정 → Notion → Notion으로 로그인**을 누르세요. 호스트 설치에서는 대시보드를 실행하는 컴퓨터에서, Docker에서는 `TP_ADMINS` 계정으로 연결합니다. Notion에서 워크스페이스와 공유할 페이지·DB를 골라 승인하면 전역 설정에 계정 이름과 워크스페이스가 표시돼요. 회사·개인 계정을 함께 쓰려면 여기서 다시 로그인하세요.
2. **프로젝트 → 설정**에서 **레포** 아래에 있는 **티켓 설정** 카드를 찾으세요. **티켓 출처**로 **Notion 데이터베이스**를 고르면 같은 카드에서 계정과 작업 DB를 선택할 수 있어요. 연결이 하나면 바로 **공유한 데이터베이스**를 고르고, 여러 개면 먼저 **연결 계정 · 워크스페이스**를 고릅니다. 새 프로젝트 마법사에서는 **작업 소스**와 **소스 설정**에서 이 항목들을 고릅니다. 연결이 없으면 안내 링크로 전역 설정을 열어 연결한 뒤 돌아오세요.
3. 작업 DB를 고르면 **가져오기 조건**이 바로 표시돼요. **담당자 열**에 사람 속성(예: `개발 담당`)을 고르세요. 기본값 **연결한 나**는 선택한 연결을 승인한 사람입니다. 다른 팀원을 고르거나 **전체**로 바꿀 수 있어요. **태그 열**은 선택·다중 선택, **상태 열**은 상태·선택 속성을 지원합니다. 예를 들어 담당자를 팀원 한 명, `라벨` 값을 `tp`, `상태` 값을 `할 일`로 고르면 세 조건을 모두 만족하는 페이지가 들어와요. 담당자를 **전체**로 바꾸면 태그와 상태 조건만 적용합니다.
4. **티켓 미리보기**에서 일치한 수와 제목을 확인하세요. 새 프로젝트는 다음 단계에서 레포를 고르고 마지막 **확인 → 티켓 미리보기**에서 자동 시작 대상도 확인할 수 있어요. **자동 시작**은 선택한 태그 열에 전역 작업 태그(`asana_tag`, 기본 `tp`)가 있고 현재 프로젝트의 레포와 티켓 단계상 투입 대기열에 들어갈 페이지입니다. 태그 열을 비우면 조회용 티켓으로 들어와요. 수동 지정한 작업 레포를 삭제하면 지정이 풀려요. 프로젝트에 레포가 하나면 그 레포를 사용하고, 여럿이면 티켓에서 고릅니다. 레포가 없으면 보드에서 지정할 수 있어요.
5. 미리보기는 조회만 합니다. 프로젝트를 **저장**하면 다음 동기화부터 보드와 작업 대기열에 적용돼요. 조회에 실패하면 현재 조건으로 동기화에 성공할 때까지 새 작업의 시작을 보류해요. 여러 프로젝트가 같은 우선순위와 가져오기 조건으로 한 페이지에 일치하면 설정 순서가 앞선 곳에서 작업을 시작합니다.
6. 보드의 **가져온 미완료 티켓**에는 담당자·태그·상태 조건을 만족한 티켓이 포함돼요. 작업을 시작할 때 페이지 본문과 누락된 하위 블록을 읽습니다. 끝까지 읽을 수 없으면 해당 티켓은 대기열에 두고 로그에 이유를 남겨요. 권한 오류가 표시되면 해당 페이지를 Notion 연결에 공유하세요.
7. 미리보기 아래의 **프로젝트 소속과 하위 작업**, **마일스톤**, **마감일**, **작업 단계별 Notion 상태**는 필요할 때 펼치세요. **가져올 상태**와 단계별로 기록할 값은 같은 **상태 열**에서 각각 고릅니다. 예를 들어 **가져올 상태**는 `할 일`, **작업 시작 · 작업 중**은 `진행 중`, **운영 배포 확인**은 `완료`로 설정하세요. **가져올 상태**를 **전체**로 두고 단계별 기록만 설정할 수도 있어요. 각 단계의 기본값은 **반영 안 함**입니다. 작업을 시작하면 가져오기 조건에서 빠져도 처음 프로젝트가 같은 페이지 ID를 추적하고, 운영 반영까지 확인하면 설정한 값으로 바꿉니다.

**공유 작업 DB에서 프로젝트 구분하기**

**프로젝트 소속과 하위 작업**에서 팀에 필요한 항목을 설정하세요.

- **상위 항목 관계 열**에서 Notion의 하위 항목 기능이 만든 부모 방향의 열을 고르세요. 이 열은 같은 작업 DB를 가리킵니다. 하위 작업을 만들 때 여기에 부모를 연결하고, 가져올 때는 이 열을 따라 부모의 프로젝트를 확인해요.
- **프로젝트 행이 있는 DB**에서 작업 DB 또는 별도로 공유한 프로젝트 목록 DB를 고른 뒤 **프로젝트 행**을 선택하세요. 작업 DB에서 그 행을 가리키는 열을 **작업 DB의 프로젝트 관계 열**로 고르면 일반 작업과 하위 작업을 만들 때 모두 프로젝트 행이 연결돼요. 프로젝트 행과 작업이 같은 DB에 있고 프로젝트 행 아래에 작업을 두는 팀은 상위 항목 관계 열만으로도 그 행의 하위 작업을 가져올 수 있어요. DB·행·관계 열은 ID로 저장되어 이름을 바꿔도 연결이 유지됩니다.
- 티켓 번호나 프로젝트명을 쓰는 팀은 **문자열을 검사할 열**과 **포함할 문자열**만 설정해도 됩니다. 예를 들어 `프로젝트명`에 `toothpaste`가 들어가거나 `업무 코드`의 값이 `모바일 / TP-17`일 때 `TP-`가 일치해요. 제목, 텍스트, 문자열 수식, 기본 고유 ID를 지원하며 대소문자를 구분합니다. 고유 ID는 접두사와 번호를 합친 `TP-17`로 비교해요.

직접 연결된 프로젝트 행을 먼저 확인합니다. 연결이 없으면 상위 작업의 소속을 따르고, 거기서도 소속을 찾지 못하면 현재 작업의 문자열을 확인해요. 부모가 지정한 프로젝트 행 자체인 경우도 포함합니다. 예를 들어 `TP-17 로그인 오류` 아래의 `재현 테스트`는 자신의 업무 코드가 비어 있어도 부모의 프로젝트에 속해요. 미리보기와 동기화 모두 가져올 작업 **자신의** 담당자·태그·상태 조건을 적용합니다.

공유 DB에서 관계 열을 삭제하거나 연결 대상 DB를 바꾸면 그 열을 선택한 프로젝트의 미리보기와 동기화에 오류가 표시돼요. 다른 프로젝트는 소속을 확인한 작업을 계속 가져옵니다.

문자열을 검사할 열이 삭제되거나 지원하지 않는 유형으로 바뀌면 그 열을 선택한 프로젝트에 오류가 표시돼요. 다른 프로젝트는 읽을 수 있는 문자열 열을 상위 작업부터 현재 작업까지 검사해요. 부모의 업무 코드가 비어 있어도 자식에 `모바일 / TP-17`이 있으면 자식은 `TP-` 조건에 일치합니다.

소속을 확인할 수 없는 작업은 미리보기에서 빠지고, 이미 가져온 작업은 기존 소속을 유지한 채 자동 시작을 보류해요. 오류가 표시된 프로젝트에서 올바른 열을 다시 고르면 다음 동기화에서 소속을 다시 확인합니다.

**Notion 페이지 편집**

프로젝트 채팅에서 “이 DB에 버그 티켓을 만들어 줘” 또는 “이 티켓을 진행 중으로 바꾸고 긴급 태그를 붙여 줘”라고 요청하세요. 터미널과 에이전트는 같은 명령을 사용합니다. 아래 `app`은 프로젝트 설정의 ID이고, `NT-…`에는 생성 결과나 보드의 티켓 키를 넣으세요. 생성 결과에 Notion 링크가 함께 표시됩니다.

```sh
tp notion update NT-… --title "모바일 로그인 오류" --assignee me --due 2027-01-15
tp notion status NT-…                  # 현재 DB의 선택지 조회
tp notion status NT-… "진행 중"
tp notion tag NT-… 긴급
tp notion tag NT-… 긴급 --remove
tp notion comment NT-… "수정 PR을 열었습니다. https://github.com/example/app/pull/42"
```

Notion 하위 티켓을 만들 때는 같은 작업 DB의 부모 키(`NT-…`)나 gid(`notion:…`)를 `--parent`에 넣으세요.

`update --body`는 페이지 본문 전체를 Markdown으로 교체합니다. 담당자와 마감일은 `none`으로 해제할 수 있어요. 사람 열이나 날짜 열이 여러 개면 프로젝트에서 **담당자 열**과 **마감일 열**을 지정하세요. 다중 선택 열에서는 위 명령 후 `버그`가 남고, 단일 선택 열에서는 추가한 값으로 교체되며 그 값을 제거하면 비워져요. 대기 중인 티켓의 속성을 편집하면 다음 동기화에서 가져오기 조건을 다시 확인하고 작업을 시작합니다.

가져오기에는 기존 읽기 권한을 계속 사용할 수 있어요. 쓰기를 사용하려면 운영자가 Notion OAuth 앱에서 페이지 생성용 **콘텐츠 추가(Insert content)**, 상태·태그·속성·본문 변경용 **콘텐츠 수정(Update content)**, 댓글용 **댓글 추가(Insert comments)** 중 필요한 권한을 켭니다. **전역 설정 → Notion → Notion으로 로그인**에서 같은 계정과 DB를 다시 승인하세요. [Notion 연결 권한](https://developers.notion.com/reference/capabilities)

단계 변경은 먼저 보드에 기록되고, 호스트의 `tp tick`이 대기 중인 상태를 백그라운드에서 Notion에 반영합니다. 실패하면 로그에서 이유를 볼 수 있고 5분 뒤부터 다시 시도해요. 그사이 같은 티켓이 다른 상태를 쓰도록 설정한 단계에 도달하면 새 상태를 보냅니다.

**단계**(보드에 보이는 이름)
- 대기: 투입 대기, 레포 선택 필요, 매핑 없음(프로젝트에 연결된 레포 없음), 선행 작업 대기, 수정 대기, 충돌 대기, 작업 완료 대기(마일스톤).
- 작업 중: 투입됨, 작업 중, 하위작업 진행 중(마일스톤).
- **막힘**에는 에이전트의 질문, 규칙 위반, 시간 초과와 Notion 마일스톤의 **마일스톤 연결 확인**, **staging 설정 필요**가 표시됩니다. `tp guide blocked`.
- PR / 리뷰 대기: 에이전트 완료, 리뷰 대기.
- 리뷰 완료: AI 리뷰 통과, staging 머지 중.
- 배포 대기: staging에 들어감, 머지됨, 배포 중, 마일스톤에 합침.
- 완료: 프로덕션에서 확인됨. 그 밖에 닫힘(배정 해제, 완료됨), 건너뜀.

동시에 일하는 티켓 수는 설정 `max_active_runs`(기본 3)까지이고, 이미 투입된 에이전트가 막히면 답장하거나 그만둘 때까지 자리를 차지합니다. 충돌 수정과 리뷰 수정이 새 티켓보다 먼저 자리를 받아요.
에이전트가 `agent_max_min`(기본 240분)보다 오래 돌면 멈추고 막힘이 됩니다.

**여러 레포에 걸친 티켓**: 프로젝트에 레포가 여럿이면 티켓은 "레포 선택 필요"가 됩니다. 자동화가 확실한 경우에만 레포를
고르고, 애매하면 사람이 보드 카드의 레포 선택에서 고릅니다(`tp assign <키> <레포>`). 한 티켓은 한 레포에서만 작업해요.
여러 레포가 필요하면 레포별로 태스크를 나누세요.

**의존 관계**: Asana의 dependency(선행 태스크)가 끝나지 않았으면 "선행 작업 대기"입니다. 선행 태스크가 완료되거나, 그 PR이
같은 프로젝트 레포의 기능 base 브랜치(예: staging)에 머지되면 풀리고, 이때 worktree는 그 브랜치에서 시작합니다.

**건너뛰기**: 투입하지 않을 티켓은 건너뜀(`tp skip <키>`, 되돌리기 `tp unskip <키>`).

## milestone · 마일스톤
하위 태스크를 모아 한 번에 staging과 프로덕션에 올리기.

**프로젝트에서 만들기**

```sh
tp milestone create --project app --title "모바일 로그인" --subtask "화면 수정" --subtask "회귀 테스트"
```

부모를 먼저 만들고 각 제목을 하위 티켓으로 연결해요. 부모만 만들려면 `--subtask`를 생략하세요. 나중에 추가하려면 `tp ticket create --project app --title "추가 검증" --milestone <부모 gid>`를 사용하세요. Asana 하위 티켓에는 작업 태그와 담당자 `me`를 적용해요. Notion 하위 티켓에는 담당자와 상태를 가져오기 조건에 맞추고, 태그 열에 가져오기 태그와 작업 태그를 함께 넣습니다. 태그 열을 골라야 하며 두 태그가 다르면 다중 선택 열이 필요해요. 마일스톤 판별 태그는 하위 티켓의 태그와 구분하세요. `--subtask`나 `--milestone`으로 하위 티켓을 요청할 때 이 조건을 충족하지 않으면 페이지를 만들기 전에 `milestone_unsupported`를 반환합니다. 동기화 후 첫 하위 티켓이 투입되면 브랜치가 생겨요.

결과의 `subtasks`에 생성이 확인된 하위 티켓의 키와 링크가 나옵니다. 하위 티켓 생성 후 로컬 저장 등에 문제가 생기면 오류 JSON의 `warnings`에 사유와 `created` 정보가 나와요. `failed` 항목은 사유와 원격 생성 여부를 확인한 뒤 필요한 하위 티켓만 추가하세요. 부모의 생성 직후 오류가 발생하면 `created`에 부모 정보가 나와요. 오류 사유를 확인한 뒤 그 `gid`로 하위 티켓을 추가하세요.

GitHub에서는 `milestone_tag` 라벨을 붙인 부모 이슈와 `tp` 라벨을 붙인 하위 이슈를 만듭니다. 다른 레포의 부모는 `--milestone 'gh:example/api#12'`처럼 지정할 수 있어요. 부모와 자식 레포의 소유자가 같아야 합니다. 하위 PR이 머지된 뒤 이슈의 부모가 바뀌어도 실제 머지된 브랜치의 배포를 추적해요. 프로덕션 반영이 확인되면 하위 이슈를 닫고, 모든 레포의 반영과 하위 이슈 종료를 확인하면 부모 이슈를 닫습니다. GitHub 오류로 닫기에 실패한 이슈는 다음 tick에서 재시도해요.

**Asana에서 만들기**

부모 태스크에 설정 `milestone_tag`의 태그(새 설치 기본 **`tp-milestone`**)를 붙이고, 하위 태스크에는 평소처럼 티켓 태그(`asana_tag`)를 붙입니다.
staging 열차 레포, `pr_into_staging` 레포, 배포 규칙에서 별도의 staging 브랜치로 머지하는 레포가 참여합니다.
열차나 `pr_into_staging` 레포에서 staging 머지를 끄면 기존 하위 티켓은 마일스톤 브랜치를 유지하고 **staging 설정 필요**에서 기다려요.

**Notion에서 만들기**

1. 작업 DB를 Notion 연결에 공유하세요. 마일스톤 행도 여기에 두려면 같은 DB를 가리키는 관계 열과, 마일스톤을 구분할 선택 또는 다중 선택 열을 만드세요. 별도의 마일스톤 DB를 쓸 때는 그 DB도 연결에 공유하고 작업 DB에 마일스톤 DB를 가리키는 관계 열을 만드세요.
2. **프로젝트 → 설정 → 티켓 설정**에서 **마일스톤**을 펼치고 **마일스톤 DB**와 **작업 DB의 마일스톤 관계 열**을 고르세요. 작업 DB를 골랐다면 **마일스톤 판별 열**(예: `유형`)과 **마일스톤 태그**(예: `마일스톤`)도 골라 저장합니다. 열이나 태그의 이름을 바꿔도 연결은 유지됩니다. 판별 열이나 선택지를 삭제하면 이 작업 DB를 쓰는 모든 프로젝트의 동기화가 멈춥니다. 해당 태그를 지정한 프로젝트 설정에서 다시 골라 주세요.
3. 같은 DB에서는 마일스톤 행에 지정한 태그를 붙이세요. 작업 DB를 여러 프로젝트가 공유하면 한 프로젝트에서 지정한 마일스톤 행도 모든 프로젝트의 티켓 미리보기와 투입 대상에서 빠집니다. 이미 실행 중인 작업에 이 태그를 붙이면 기존 실행이 보드의 **막힘**에 표시됩니다. 하위 작업의 관계 열에는 그 프로젝트가 지정한 태그가 붙은 마일스톤 행 하나를 선택하세요. 별도 마일스톤 DB를 쓸 때는 그 안의 행을 태그 없이 연결할 수 있어요. 관계가 비어 있으면 일반 티켓으로 진행합니다. 여러 행에 연결하거나 같은 DB에서 해당 프로젝트의 태그가 없는 행에 연결하면 **마일스톤 연결 확인**이 표시되고 투입을 보류합니다. 연결을 고치면 다음 동기화에서 다시 진행합니다.
4. 하위 작업을 맡을 레포의 **프로젝트 → 설정 → 레포별 설정 → 배포**에서 **staging 브랜치 사용**을 켜고, 중간·prod 브랜치와 다른 staging 브랜치를 지정하세요. **배포 방식**에서 **staging**을 선택하고 저장합니다. 레포가 정해졌을 때 이 설정이 필요하면 보드의 **막힘** 열에 **staging 설정 필요**가 표시됩니다. 설정을 마치면 다음 동기화에서 투입 대기로 돌아갑니다. 이미 리뷰를 마친 PR은 **배포 → 티켓 배포**에서 같은 설정 안내를 확인할 수 있어요.

열린 하위 작업 PR의 관계를 바꾸면 다음 PR 스캔에서 새 대상 브랜치를 확인합니다. 관계를 비우면 `pr_into_staging`으로 지정한 `dev` 같은 일반 작업용 브랜치로 돌아가며, 이때는 **staging** 배포 방식을 켤 필요가 없어요. 일반 작업용 브랜치를 따로 쓰지 않으면 사용 가능한 staging 브랜치로, 이 경로도 없으면 GitHub 기본 브랜치로 돌아갑니다.

이전 마일스톤의 다른 커밋이 따라가면 PR 대상을 유지하고 로그에 이유를 남깁니다. 이때는 해당 작업의 커밋만 새 대상 브랜치 위로 옮기세요. 관계를 비운 작업은 PR 대상이 바뀐 뒤부터 레포의 일반 배포 규칙을 따릅니다. 이미 머지된 PR은 머지 당시의 마일스톤과 함께 배포합니다.

작업 DB를 공유할 때 한 프로젝트가 `유형` 열의 `마일스톤`을 판별 태그로 쓰면, 어느 프로젝트에서도 그 열의 `마일스톤`을 **작업 단계별 Notion 상태**로 지정할 수 없어요. 예전 설정에 이런 조합이 있으면 해당 단계의 상태 반영을 보류하고 로그에 이유를 남깁니다. 상태값이나 열을 고치면 다음 재시도에서 새 설정을 사용합니다.

프로젝트의 **작업 단계별 Notion 상태 → 운영 배포 확인**을 지정하면, 모든 레포가 운영에 반영된 뒤 마일스톤 행에도 그 상태를 기록합니다. 같은 DB에서는 작업의 상태 열을 사용합니다. 마일스톤 행에 운영 배포 상태를 쓸 열은 그 DB의 모든 마일스톤 판별 열과 따로 골라 주세요. 별도 마일스톤 DB에는 작업 DB의 상태 열과 같은 이름의 상태 또는 선택 열을 쓰거나, 상태 열을 하나만 두세요. 그 열에 작업 DB와 같은 이름의 완료 선택지가 있어야 합니다.

**흐름**
1. 첫 하위 태스크가 투입되면 그 레포에 staging에서 `milestone/<부모 gid>` 브랜치가 생기고, 마일스톤 티켓(하위작업 진행 중)이 생깁니다.
   Notion은 마일스톤 행의 페이지 ID를, GitHub는 `milestone/gh-example-api-12` 같은 브랜치 이름을 씁니다. 하위 태스크 PR은 이 브랜치를 향합니다.
2. AI 리뷰가 승인하고 tp 검사가 통과한 하위 태스크 PR은 다음 tick에 버튼 없이 마일스톤 브랜치에 머지됩니다(마일스톤에 합침).
   하위 태스크가 진행 중인 동안 staging이 마일스톤 브랜치에 계속 합쳐져 어긋나지 않아요.
3. 모든 하위 태스크가 브랜치에 들어가면(또는 완료, 닫힘, 건너뜀) 마일스톤 티켓은 "작업 완료 대기"로 멈춥니다.
4. 마일스톤 화면에서 **마일스톤 작업 완료**를 누르면(CLI는 `tp milestone-done <부모 gid>`, Notion은 `tp milestone-done notion:<페이지 ID>`) 마일스톤 브랜치에서 staging으로 가는 PR이
   열립니다. 하위 태스크가 진행 중이면 거절되고, 누른 뒤에 하위 태스크가 다시 진행 중이 되면 자동으로 풀립니다.
5. 그 다음은 일반 티켓과 같습니다: AI 리뷰, 수정/충돌 에이전트, 사람의 staging 머지 승인, 배포 열차.
6. 프로덕션에서 확인되면 마일스톤 티켓과 합쳐진 하위 태스크가 완료되고, 마일스톤의 모든 레포가 반영되면 부모 태스크도 완료됩니다.

**나중에 추가한 하위 태스크**: 마일스톤 PR이 열려 있는 동안 진행 중인 하위 태스크가 생기면 마일스톤 티켓은 다시 하위작업 진행 중이
되고(AI 리뷰, staging 승인 없음) 그 태스크가 브랜치에 들어갈 때까지 기다립니다. 들어가면 다시 작업 완료 대기가 되니 **마일스톤 작업 완료**를 한 번 더 누르세요. 마일스톤 PR이 머지된 뒤에 합쳐진 하위 태스크는
다음 회차가 됩니다. 각 회차는 자기가 실어 나른 하위 태스크만 완료해요.

**dev 서버**: 마일스톤 화면의 레포별 dev 서버 패널에서 `milestone/<부모 gid>`를 띄워 하위 태스크를 함께 시험할 수 있어요.

## review · 리뷰
AI 리뷰, 수정 라운드 상한, tp 검사, 사유를 적고 승인하기.

- 에이전트가 PR을 열고 리뷰 준비를 알리면 리뷰 자동화가 새 head 커밋을 리뷰하고 결과를 PR 댓글과 대시보드에 남깁니다.
  판정은 괜찮음(approve), 수정 필요(changes), 막힘(blocked)입니다.
- **수정 필요** → 수정 대기 → 에이전트가 같은 worktree에서 리뷰를 받아 고치고 push → 새 head를 다시 리뷰(지난 리뷰 이후 바뀐 부분만).
- **수정 라운드 상한**: 설정 `review.max_rework_rounds`(기본 3, 0 = 무제한, 레포 리뷰 설정에서 따로 정할 수 있음)번 고친 뒤에도 수정 필요가 나오면 사람에게 막힘으로 넘어옵니다.
  답장하면 에이전트가 다시 돌고 횟수가 새로 시작돼요.
- **충돌**: PR이 base와 충돌하면 충돌 대기 → 충돌 에이전트가 base를 합쳐 push → 다시 리뷰. 승인 요청이 있었다면 지워집니다.
- **tp 검사**: 레포 설정의 검사 명령(`repo.<이름>.checks`, 또는 GitHub 체크를 읽는 `ci`)을 PR head마다 돌립니다. 실패하면
  수정 필요 리뷰로 에이전트에게 돌아가고 수정 라운드에 포함됩니다. 카드의 검사 배지를 누르면 로그가 보여요. 검사가 없는 레포는 "검사 없음".
- **승인**: 리뷰 완료 카드의 **<staging> 머지 승인**을 누르면 5분 안에 호스트가 head, base, 충돌을 다시 보고 staging에 머지합니다.
  취소는 같은 자리에서(`tp approve <키> --cancel`).
- **사유를 적고 승인하기**: 검사가 통과하지 않았거나 AI 판정이 수정 필요/막힘이어도, 사람은 사유를 적고 승인할 수 있어요
  ("사유 적고 승인…", "사유 적고 검사 무시…"; `tp approve <키> --override "사유"`, `--override-review "사유"`, `tp check-override <키> "사유"`).
  그 head에만 적용되고 카드에 사유가 남습니다.

## blocked · 막힘
BLOCKED의 뜻, 답장, 그만두기.

- **막힘**은 사람이 답해야 진행되는 상태입니다. 에이전트가 `BLOCKED: <질문>`을 남겼거나, 리뷰 수정 라운드 상한에 닿았거나,
  시간 초과로 멈췄거나, 에이전트가 완료 신호 없이 끝났거나(마지막 메시지가 남음), 규칙 위반(`BLOCKED: 규칙 위반: ...`)일 때입니다.
- **규칙 위반**: 에이전트가 base 브랜치(main, staging, production 등)에 티켓 커밋을 push했거나, 에이전트가 도는 중에 PR이 머지되면
  에이전트를 멈추고 막힘으로 만듭니다. 자동으로 되돌리지는 않아요.
- **답장**: 보드 카드의 "에이전트에게 답장" 칸에 답을 쓰고 **답장하고 재실행**을 누르면 5분 안에 같은 worktree에서 에이전트가 이어서 일합니다.
- **그만두기**: 카드의 그만두기는 에이전트를 멈추고 실행을 포기하고 티켓을 건너뜀으로 바꿉니다(`tp drop <키>`). 자리가 비고,
  worktree, 브랜치, 열린 PR은 남으며 Asana는 건드리지 않아요. 건너뜀 티켓은 에이전트와 직접 띄운 서버가 끝나면 worktree를 정리하고 `tp dev` 서버도 함께 꺼요.

## deploy · 배포
배포 방식 4가지, 배포 열차, 프로덕션 확인과 완료 처리.

레포마다 배포 규칙(설정 → 프로젝트 → 레포 → 배포, `repo.<이름>.deploy`)이 브랜치(staging → prod)와 쓸 수 있는 방식을 정합니다.
staging 열차 레포와 `pr_into_staging` 레포는 티켓 브랜치를 staging에서 만들고 PR도 staging으로 엽니다.

**방식**(배포 화면 버튼, `tp deploy <방식> [--ticket 키] [--repo 레포]`)
1. **staging**(티켓 → staging): AI가 승인한 PR을 staging 브랜치에 머지합니다(리뷰 완료 카드의 머지 승인).
2. **direct**(티켓 → prod, staging 건너뜀): PR base가 이미 prod면 그대로 머지, 아니면 prod에서 `release/<키>-<시각>` 브랜치를 만들어
   PR의 커밋을 cherry-pick해 머지하고, 원래 PR도 자기 base에 머지합니다.
   Notion 마일스톤과 그 하위 작업은 **direct**를 켠 레포에서도 마일스톤 PR의 staging 머지 승인 후 함께 배포합니다.
3. **promote**(staging의 PR → prod): 티켓 배포 표에서 staging에 머지된 PR마다 한 행을 표시합니다. 그 행의 **prod 반영**은 선택한 PR의 커밋만 cherry-pick합니다.
   CLI에서 PR을 지정하려면 `tp deploy promote --ticket 키 --pr URL`을 실행합니다. `--pr`을 생략하면 최신 실행의 PR을 사용합니다.
4. **all**(staging 전체 → prod): staging 파이프라인이 초록이면 `staging -> prod` PR을 머지합니다. toothpaste 밖에서 들어간 커밋도 같이 나가요.

버튼은 요청만 기록하고, 다음 tick이 머지 → 프로덕션 파이프라인 확인까지 진행합니다. 레포마다 한 번에 하나씩 순서대로 돌고, 자동 롤백은 없습니다.
배포 화면의 "staging에 있고 프로덕션에 없는 것"은 나갈 커밋과 AI 메모(배포 추천 / 확인 필요 / 보류)를 보여 줄 뿐, 배포는 버튼으로만 합니다.
배포 화면의 대기 PR 수와 배포 열차는 레포의 staging 브랜치에 머지되었고, 배포 기록이나 프로덕션 반영 기록이 아직 없는 PR을 기준으로 집계합니다.

**배포 열차**: 열차 레포(`deploy.repos.*.train`)는 설정 `release`의 평일 시간대(기본 월-금 10:00부터 120분, Asia/Seoul)에
자동으로 `staging -> main`을 머지하고 프로덕션 파이프라인을 기다립니다. staging에 승인된 PR이 아닌 커밋이 있거나 staging 파이프라인이
초록이 아니면 그날 열차는 멈춰요. 배포 화면에서 다음 시각, 자동 배포 레포의 staging 대기 PR 수, 보류 스위치를 볼 수 있습니다.
대기 PR 수에는 다른 배포에서 처리 중이거나 다음 마일스톤 PR을 기다리는 PR도 포함됩니다. 열차가 없는 레포의 staging PR은
배포 화면에서 promote나 all로 올립니다.

**프로덕션 확인과 완료**: 머지는 배포가 아닙니다. 티켓은 프로덕션이 실제로 그 커밋을 돌리는 것이 확인될 때까지 배포 대기에 있고,
확인되면 완료가 되며 Asana 태스크를 완료 처리합니다(GitHub 이슈는 댓글을 달고 닫음). toothpaste 밖에서 머지된 PR도 같은 방식으로
확인합니다. 무엇으로 확인할지는 레포 설정 → 배포의 **반영 확인**에서 골라요: CodePipeline, GitHub Actions workflow, 또는
**최신 GitHub Release에 포함**(`prod.release: true`, 릴리즈를 받아 업데이트하는 toothpaste 자신처럼). 완료된 티켓의 worktree와 로컬 브랜치는 자동으로 지워집니다(원격 브랜치와 PR은 남음).

## agent · 에이전트 규칙
에이전트(티켓, 채팅)가 해도 되는 것과 안 되는 것.

- **안 됨**: PR 머지, main/master/staging/production 같은 base 브랜치에 push, force-push, 배포, 프로덕션 데이터나 secret 변경.
  base 브랜치 push와 실행 중 머지는 매 스캔에서 검사되고 규칙 위반으로 막힙니다.
- **상태 변경은 대시보드에서**: 승인, 배포, 마일스톤 작업 완료, 그만두기, 건너뛰기는 사람이 대시보드에서 합니다. 에이전트가 대신 누르지 않아요.
- **티켓 에이전트**: 자기 worktree에서만 작업하고, draft PR을 연 뒤 `tp ws-set --status in-review --comment "PR #<n> ready: ..."`로
  끝을 알립니다. 사람의 결정이 필요하면 `tp ws-set --status todo --comment "BLOCKED: <질문>"`을 남기고 멈춥니다.
- 티켓 화면을 확인할 때는 worktree에서 `tp dev start --worktree .`을 실행해요. 레포 설정이나 package.json에서 명령과 포트를 찾고,
  같은 worktree에서 tp가 띄운 서버가 있으면 재사용해요. `--port N`으로 원하는 포트를 지정할 수 있고, 다른 프로세스가 사용 중이면 빈 포트를 골라요.
  포트가 열리면 URL, 포트, `data/dev/` 아래의 로그 경로를 출력해요. 60초 안에 열리지 않으면 로그 경로와 함께 실패를 알려요.
  worktree에 `.nvmrc`가 있으면 nvm에 설치된 버전 중 조건에 맞는 최신 버전을 사용해요. nvm에 없어도 현재 Node 버전이 맞으면 그대로 써요.
  `npm run dev` 같은 패키지 스크립트로 Vite를 띄워도 Vite에 선택된 포트를 전달해요. 직접 만든 서버는
  레포의 dev 서버 명령에 `{port}`를 넣거나 스크립트에서 `PORT` 환경변수를 읽으세요.
  `tp dev status --worktree .`으로 상태를 확인하고, `tp screenshot --url <출력된 URL> --repo . --out shot.png`로 캡처한 뒤
  `tp dev stop --worktree .`으로 종료해요. 티켓 worktree를 자동으로 정리할 때도 tp가 띄운 서버를 함께 꺼요.
- **채팅 에이전트**: 레포 checkout은 읽기 전용입니다. 실험은 /tmp clone에서. 티켓과 마일스톤을 만들어 달라고 하면 `tp ticket create`와 `tp milestone create`를 사용합니다.
- 기존 Notion 티켓은 프로젝트에 연결된 DB에서 `tp notion`으로 편집하고 댓글을 답니다. 명령 예시는 `tp guide ticket`에 있어요.
- **Asana 편집**(`tp asana comment|update|tag`): tp가 토큰을 가지고 있으니 에이전트는 토큰을 찾거나 쓰지 않습니다.
  사용자나 티켓이 요청할 때, 또는 자기 티켓에 짧은 메모를 남길 때만 씁니다. 티켓 태그(`asana_tag`)를 붙이면 바로 티켓 에이전트가 투입돼요.
  파이프라인에 있는(실행 기록이 있는) 티켓은 완료 처리하거나 담당자를 바꿀 수 없습니다. 프로덕션 반영 후 toothpaste가 완료합니다.
  설정 `agent_asana_write`가 꺼져 있으면 Asana는 읽기 전용이고, 자동화 단계는 언제나 쓸 수 없습니다.
- 사용법이 궁금하면 `tp guide`로 주제를 보고 `tp guide <주제>`로 읽습니다.
- **어떤 도구로 도나**: **설정 → 에이전트**의 카드 세 개가 역할별 도구(claude/codex/agy), 모델, 추론 강도를 정해요(설정 `agents`).
  **투입**은 티켓 작업(새 티켓, 리뷰 수정, 충돌, 답장 뒤 재실행), **리뷰**는 AI PR 리뷰, **검사**는 판단을 맡는 자동화(배포 diff 요약,
  worktree 정리 판정, 저장소 고르기)예요. 우선순위는 레포별 에이전트 설정(티켓 작업과 프로젝트 채팅) > 역할 카드 > 기본 도구(`agent`).
  카드를 비우면 기본 도구를 따라요. 맨 위 **활성 계정**은 Claude, Codex, Antigravity의 설치, 버전, 로그인 방식(CLI 로그인, tp 토큰, API 키), 계정을 보여 주고, 로그인하지 않은 도구는 고를 수 없어요.
- **에이전트 로그인**(활성 계정, 시작하기에서 같은 화면): 이 컴퓨터(127.0.0.1)에서만, Docker 모드에서는 `TP_ADMINS`만 할 수 있어요.
  - **codex**: 로그인을 누르면 코드와 주소가 나와요. 주소를 열어 코드를 넣으면 자동으로 끝나요(15분 안). 로그아웃은 `codex logout`과 같아요.
  - **claude**: 로그인을 누르면 Claude 로그인 주소가 나와요(`claude setup-token`, Claude 구독 필요). 브라우저에서 받은 코드를 붙여넣으면 1년짜리 토큰을 tp에 저장해요.
    구독이 없으면 **API 키**(`ANTHROPIC_API_KEY`)를 붙여넣어요. Anthropic에 확인한 뒤에만 저장해요.
  - tp에 저장한 claude 토큰이나 키는 claude CLI 자체 로그인(`~/.claude`, 키체인, 환경변수)이 없을 때만 에이전트(티켓, 채팅, 자동화)에 넘겨요. 이미 CLI로 로그인돼 있으면 그대로 그 로그인을 써요.
  - claude 로그아웃은 tp에 저장한 토큰과 키만 지워요. CLI 자체 로그인은 그대로예요.
  - 고급(터미널): `claude setup-token`을 실행하고 출력된 토큰을 claude 카드의 **토큰 붙여넣기**에 넣어요. CLI 자체 로그인은 `claude` 실행 후 `/login`, `codex login`.
    Docker 모드에서는 저장소 폴더에서 `cd docker && docker compose exec tp claude`처럼 컨테이너 안에서 실행해요.
  - **Antigravity (agy)**는 tp가 실행되는 호스트나 컨테이너에 설치하세요. [공식 설치 안내](https://antigravity.google/docs/getting-started/)
    **Google 계정 로그인**을 눌러 브라우저의 코드를 붙여넣거나 같은 환경의 터미널에서 `agy`를 열어 로그인할 수 있어요.
    **Gemini API 키**로 연결하려면 결제가 활성화된 Google AI Studio 프로젝트의 키를 넣으세요. tp가 키를 확인해 비밀 저장소에 보관하고 agy 실행에 전달해요.
    터미널에서 설정했다면 `~/.gemini/antigravity-cli/settings.json`의 `modelProvider`가 `gemini`이고 tp 실행 환경에 `GEMINI_API_KEY`가 있어야 해요.
  - Antigravity에는 연결된 계정의 모델이 표시돼요. **Gemini 4 Neon**은 Google AI Free·Plus에 제공되지 않아요.
    유료 Pro, 대상 프리미엄 기기의 Pro 체험, Ultra, Enterprise 또는 Neon 이용 권한이 있는 유료 Gemini API 프로젝트가 필요해요.
    프로젝트 채팅은 같은 레포와 도구를 쓰는 동안 Antigravity 대화 ID로 이어집니다. [Google 계정의 모델 이용 조건](https://antigravity.google/docs/models) · [Gemini API의 Neon 이용 조건](https://aistudio.google.com/docs/pricing#gemini-4-neon)
  - 연결 해제는 tp에 저장한 Gemini API 키는 대시보드에서, Google 계정은 `agy`의 `/logout`으로, 직접 설정한 API 키는 `modelProvider` 설정을 제거해요.
    터미널에서 변경한 뒤 **다시 확인**을 누르면 바로 반영돼요.
- **사이드바 사용량**에는 설치와 인증이 확인된 에이전트만 표시돼요. 로그아웃하면 이전에 조회한 값이 있어도 해당 행이 사라지고, 연결된 도구가 없으면 영역도 접혀요.
  데스크톱 사이드바나 모바일 메뉴를 펼치면, 유효한 리셋 시각이 있는 Claude·Codex 한도 막대 아래에 브라우저 시간대 기준으로 `18:30 리셋`(오늘) 또는 `11/29 18:30 리셋`(다른 날)이 표시돼요.
  접힌 데스크톱 사이드바에서는 사용량 줄에 마우스를 올려 리셋 시각을 확인할 수 있어요.
  Antigravity는 `/usage`의 모델 그룹별 한도, 사용률, 리셋 시각을 표시해요. API 키 등 CLI가 계정 한도를 제공하지 않는 경우에는 조회할 수 없다고 표시해요.
  [Antigravity 사용량](https://antigravity.google/docs/cli/commands/usage)

## update · 업데이트
버전과 업데이트.

- 버전은 git 태그 `vX.Y.Z`와 GitHub Release입니다. `main`에 머지되고 테스트가 통과할 때마다 태그가 붙고, 머지한 PR의 라벨로 올라갑니다:
  라벨 없음 = patch, `minor` = minor, `major` = major. 대시보드 제목 아래에 지금 버전이 보여요.
- tp tick이 **확인 주기**(설정 `update.check_min`, 기본 360분, 최소 10분)마다 태그를 확인하고, 새 릴리즈가 있으면 사이드바에 **업데이트 vX.Y.Z**가 나옵니다. 그 화면에서 릴리즈 노트를 보고
  업데이트 버튼을 누르면 `tp update`가 돌고 대시보드가 다시 뜰 때까지 기다립니다.
- **새 릴리즈 자동 적용**(설정 → 고급 → 업데이트, `update.auto`, 기본 꺼짐)을 켜면 tick이 새 릴리즈를 찾았을 때 업데이트 버튼과
  같은 `tp update`를 직접 실행해요(릴리즈마다 한 번). 호스트에서 업데이트할 수 없는 상태(`main` 아님, 수정된 파일)면 건너뛰고
  수신함에 알려요. Docker 모드에서는 관리자가 버튼으로 시작합니다.
- 확인 주기를 기다리지 않으려면 **설정 → 고급 → 업데이트**(또는 업데이트 화면)에서 **지금 확인**을 누릅니다. 바로 태그를 가져와 마지막 확인
  시각을 갱신하고, 새 버전이면 릴리즈 노트와 업데이트 버튼이, 업데이트할 수 없는 상태(`main` 아님, 수정된 파일)면 그 이유가
  나옵니다. 사이드바 항목도 바로 바뀝니다. 가져오기에 실패하면 그 이유를 보여 줍니다.
- 터미널에서는 `bin/tp update`(또는 `--to <태그|sha>`). checkout이 `main`이고 추적 파일에 수정이 없어야 합니다. 다운그레이드는 지원하지 않아요.
- 새 Docker 설치는 설치 명령이 업데이트 관리자도 등록합니다. 이미 Docker로 실행 중이고 관리자가 없다면 호스트의 설치 저장소에서 새 버전을 가져온 뒤 `python3 -m ticket_pilot.docker_update_manager install`을 한 번 실행하세요.
  기존 에이전트와 dev 서버가 끝난 뒤 설치하세요. macOS의 launchd 또는 Linux의 사용자 systemd 서비스로 관리자를 시작합니다.
  설치 후 `TP_ADMINS` 계정으로 **업데이트**를 누르면 관리자가 GHCR에서 새 릴리즈를 받아 기존 볼륨과 사용자 ID를 유지하며 `tp`를 교체합니다.
  실행 중인 작업이 있으면 완료될 때까지 기다렸다 다시 누르세요. 새 대시보드가 뜨지 않으면 이전 이미지로 돌아갑니다.
- 호스트 설치 로그는 `~/tp-work/logs/update.log`에 있어요. Docker 진행 상태는 업데이트 화면에서, 관리자 로그는 macOS의 `docker/.update/manager.log` 또는 Linux의 사용자 systemd 저널에서 볼 수 있어요.

## lan · 로컬망 공유
사내 팀원이 GitHub 로그인으로 이 맥의 대시보드를 같이 쓰기.

- **켜는 법**: 이 맥에서(`http://127.0.0.1:<포트>`) **설정 → 고급 → 로컬망 공유**에서 허용할 GitHub 조직(예: `<your-org>`)을 입력하고
  **공유 켜기**를 누릅니다. 설정 `lan_share`에 저장되고 `launchd/install.sh`가 다시 돌아 대시보드가 `0.0.0.0`에서 열려요
  (끄면 `127.0.0.1`로 돌아가요). 켜고 끄기, 조직 바꾸기, 강제 로그아웃은 이 맥에서만 할 수 있어요.
- **팀원 접속법**: 같은 화면의 **접속 주소**(이 맥의 사설 IP:포트)를 알려 주세요. 팀원이 열면 로그인 화면이 나오고, **GitHub로 로그인** →
  github.com/login/device 에 코드 입력 → 허용 조직의 활성 멤버면 들어가요. 초대만 받은(pending) 계정은 못 들어가요.
  GitHub 토큰은 확인에만 쓰고 저장하지 않아요. 로그인은 최대 14일, 7일 동안 안 쓰면 끝나고, 하루에 한 번 조직 멤버인지 다시 확인해요
  (확인이 안 되면 다시 로그인).
- **막는 것**: 사설망(10/8, 172.16/12, 192.168/16, IPv6 ULA·link-local)이 아닌 주소는 거절해요. 쓰기 요청은 `Origin`이 접속 주소와
  같아야 해요. HTTPS가 아니라서 같은 망에서 엿볼 수 있어요. 인터넷에 공개하지 마세요.
- **위험**: 로그인한 사람은 대시보드의 모든 기능(승인, 배포, 설정, 채팅 에이전트)을 써요. 채팅 에이전트는 샌드박스 없이 이 맥에서
  내 계정으로 명령을 실행해요. 그래서 조직 멤버만 들이고, 모든 행동에 아이디를 남겨요: **전체 로그**의 "누가" 열, **모니터링 → 설정 이력**,
  AI 판정을 넘긴 승인의 PR 코멘트. 이 맥에서 한 행동은 설정의 사용자 이름(`owner_name`)으로 남아요.

## theme · 테마
대시보드 색과 글꼴 바꾸기, 내 테마 만들기.

- **고르기**: **설정 → 테마**에서 고르면 바로 미리 보이고, 아래 **저장**을 눌러야 유지돼요(설정 `theme`, 이력에 남아요). 저장하지 않고
  나가면 저장된 테마로 돌아가요. `auto`는 시스템의 라이트/다크 설정을 따라 light와 dark 사이를 오가요. 작업실 그림도 같이 바뀌어요.
- **내 테마 만들기**: `~/tp-work/themes/`(tp checkout 옆 `themes` 폴더)에 JSON 파일을 하나 만들고 **다시 불러오기**를 누릅니다.
  파일 하나가 테마 하나이고, 파일 이름(확장자 빼고)이 테마 id예요. 사내 테마는 이 폴더에만 두고 저장소에는 넣지 않아요.

  ```json
  {
    "name": "Corp",
    "base": "dark",
    "tokens": {
      "color-primary": "#2f6fde",
      "color-primary-600": "#2f6fde",
      "font-sans": "\"Pretendard\", ui-sans-serif, sans-serif"
    }
  }
  ```

- `base`(`light` 또는 `dark`): 적지 않은 토큰은 그 내장 테마 값을 써요. 토큰 이름은 `web/src/theme/tokens.css`의 변수 이름이에요
  (`color-grey-50`~`color-grey-900`, `color-primary-*`, `color-background`, `color-surface`, `color-text-main`, `color-border`, `font-sans` 등).
- 색은 `#rrggbb`만, `font-sans`는 글꼴 이름 목록만 받아요. 모르는 토큰, 잘못된 값(`;`, `}`, `url(` 등), 읽을 수 없는 JSON은 무시하고
  설정 → 테마에 경고로 보여 줘요. 선택한 테마 파일이 없어지거나 깨지면 light로 보여요.
